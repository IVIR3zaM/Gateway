# Zero-downtime Gateway VM rollouts with Sonar and Kita
status: READY
created: 2026-10-06 · updated: 2026-10-06
goal: The VM is replaced only by a deliberate CI rollout, which builds the new VM, installs Sonar and Kita on it, then flips all three hostnames at once: zero downtime for Gateway and Kita, one short 503 handover for Sonar.
verify: (cd hetzner/terraform && terraform fmt -check -recursive && terraform init -backend=false -input=false >/dev/null && terraform validate) && ASDF_SHELLCHECK_VERSION=0.10.0 uvx --from actionlint-py actionlint .github/workflows/hetzner.yml
commit: per-node
push: none
budgets: 2 tries per brief · 2 replans per node

## Decisions

- D1 Two outcomes: (a) no implicit replacement: config, site, key and image changes apply to the running VM; (b) a deliberate rollout moves Gateway, Sonar and Kita to a new VM together, with zero downtime for Gateway and Kita and a short Sonar handover (D8, D9). v2ray tunnels on the old VM drop once when it is destroyed after the drain, and clients reconnect by themselves | confirmed
- D2 Config in place: user_data becomes a stable bootstrap (packages including unattended-upgrades, v2ray at a pinned `v2ray_version` through the installer's `--version`, directories, units). Everything that changes (v2ray config, nginx.conf, origin cert and key, site, speedtest size, stats script and unit) is pushed over SSH by `terraform_data.config` per server, triggered by a hash of the rendered files plus the server id. A remote script waits for `cloud-init status --wait`, installs only files that differ, runs `nginx -t` then `systemctl reload nginx` (graceful) when nginx files changed, and restarts v2ray only when its own config changed. It depends on `hcloud_firewall.v2ray` so port 22 is open to the applier first. Its output never prints file contents | confirmed
- D3 Server lifecycle: `hcloud_server.v2ray` keeps its address, becomes for_each over slots, and gets `ignore_changes = [user_data, image]` next to any entries already there (such as `ssh_keys`); `create_before_destroy` goes; `random_id.server_suffix` is removed; the name becomes `<name>-v2ray-<slot>`, a rename in place | confirmed
- D4 Slots and roles: servers carry labels `project=gateway`, `slot=blue|green` and `role=active|standby`. Gateway reads the current servers with `data "hcloud_servers"` (`project=gateway`; a server with no `slot` label counts as blue and active) and takes a variable `rollout_step`: `none` (default) keeps every server and role; `add` adds the other slot as standby (a no-op if it exists); `promote` swaps the two roles; `retire` and `abort` destroy the standby. A local apply with defaults therefore never creates, flips or destroys a server | confirmed
- D5 In-place migration: `moved` blocks map `hcloud_server.v2ray` to `hcloud_server.v2ray["blue"]` and `null_resource.wait_for_origin` to a per-slot `terraform_data` readiness gate (Terraform 1.9+ supports that move). The first apply renames and labels the live VM, creates its config push and the origin record, and replaces no server (gate N06). The readiness gate also checks that v2ray listens on its local port | confirmed
- D6 One flip for all hosts: Gateway owns a proxied A record whose label is random (`random_id`; sensitive output `origin_hostname`) and which points at the active server. The `gw` A record also points at the active server, changed in the same apply (it stays an A record: a type change means delete and create). Sonar's and Kita's records become proxied CNAMEs to `origin_hostname` (secret ORIGIN_HOSTNAME in each app's `production` environment, local tfvars `origin_hostname`), so `promote` moves all three. Each app record changes from A to CNAME once, in N09, at a quiet time (seconds of blip) | confirmed
- D7 Apps follow every Gateway server: Kita's and Sonar's `data "hcloud_servers"` (`project=gateway`) require at least one server instead of exactly one; `terraform_data.install` becomes for_each keyed by the `slot` label, with the server id in its triggers and a `moved` block from the single instance to `["blue"]`. An app deploy during a rollout installs on both servers; after retire the stale entry leaves state with no remote action | confirmed
- D8 Sonar handover (owner chose the short handover): `hcloud_volume_attachment.data` follows the server labelled `role=active` (exactly one). A new `terraform_data.data_mount` depends on the attachment and on the active server's install; its `input` holds the active host. Create: mount the volume, enable and start Sonar, wait for `/auth/login`, run sync-emails. Destroy-time provisioner: stop and disable Sonar, unmount. Dependents are destroyed before their dependencies, so a role change runs stop and unmount on the old server → detach → attach to the new → mount and start. install.sh stops mounting and starting Sonar and only `systemctl try-restart`s it where it already runs | confirmed
- D9 Sonar's nginx answers 503 with `Retry-After: 60` and a short "Sonar is moving, back in a minute" page when its upstream is down (502/504 become 503), on either server. Expected window: from promote until Sonar's handover run finishes, about 1-3 minutes, mostly Actions start-up | confirmed
- D10 SSH agent for Sonar: a destroy-time provisioner can only read `self`, so its connection uses `agent = true` and the host from `self.input`. Sonar's CI starts `ssh-agent`, adds the deploy key and exports SSH_AUTH_SOCK; local Sonar applies need the key loaded with `ssh-add`. No private key is ever stored in state | confirmed
- D11 Rollout in CI: Gateway's dispatch input `replace_server` becomes `rollout` (`none` default, `full`, `abort`). `full` runs in one job: apply `add` → dispatch Sonar's and Kita's `ci.yml` (ref main) and wait until both succeed → apply `promote` → dispatch both and wait (Sonar hands its data over) → wait DRAIN_MINUTES (variable, default 5) → apply `retire` → dispatch both again to prune state. A failure stops the job before the next step; `abort` removes a leftover standby. DISPATCH_TOKEN (Actions read and write on Sonar and Kita) also reads their runs; a run is found by listing workflow_dispatch runs created after the dispatch | confirmed
- D12 Replacement guard: each CI plan is checked through `terraform show -json`. A push, or `rollout=none`, fails if any `hcloud_server` would be created, deleted or replaced; `add` may create exactly one; `retire` and `abort` may delete exactly one; `promote` may do neither. The guard prints only addresses and actions | confirmed
- D13 The push-time app redeploy (the `server_id` comparison and its dispatch step) goes: only a rollout replaces the VM, and the rollout deploys the apps itself | confirmed
- D14 Cross-repo nodes: Kita and Sonar changes are in this plan. Their executors work in ../Kita and ../Sonar with Write paths relative to that repo and run its checks: Kita `node --test` plus `terraform fmt -check` and `terraform validate` (after `init -backend=false`) in `deploy/terraform`; Sonar `uv run pytest -q -x && uv run ruff check .`, the same Terraform checks, and `bash -n` on its scripts. The orchestrator commits them with `git -C ../Kita` or `git -C ../Sonar`. Agents never push; pushes are owner gates | confirmed
- D15 Agents never read or print state, `terraform.tfvars`, `backend.hcl`, `.terraform/`, keys or secrets, and never plan or apply against R2; the owner does that in gates N06, N09 and N10. Pre-authorized for agents: fmt, `init -backend=false`, validate, `terraform test` with mock providers, actionlint through uvx, `bash -n`, and read-only `gh` calls that list names or runs | confirmed
- D16 The repos and their Actions logs are public: no hostname (the origin label included), IP, email or token goes into a tracked file, commit or log; the new CI steps keep the existing IP and id filters and never print outputs | confirmed
- D17 Independent of the personal-ssh-key plan: either can run first; code here keeps `ignore_changes` entries and SSH variables already present, and briefs name resources by address, not by line | confirmed
- D18 Tests: Gateway's slot and role logic is covered by `terraform test` files in `hetzner/terraform/tests/` with mock providers and `override_data`: for each `rollout_step`, from a mocked server list, the planned slots, roles, labels and record targets | confirmed
